# MeishiLink MVP 設計

feature-slug: `mvp`
date: 2026-05-08
status: draft (要ユーザー承認)

---

## 0. 目的

紙名刺の管理難 (溜まる・検索不可・vCard 手入力面倒) を解消する Web 名刺アプリ。
登録ユーザーは自身の Web 名刺を作成し QR で共有、閲覧者は登録不要で vCard ダウンロード または ブラウザローカル (IndexedDB) に保存して一覧管理できる。
MVP の DoD は P0 + P1 全機能が `npm run dev` 単体でローカル動作完結すること。

---

## 1. スコープ

### P0 (必須)
1. ユーザー登録 (Magic Link / Google OAuth) → ダッシュボード
2. 名刺情報入力フォーム (氏名・会社名・部署・役職・TEL・Email・住所・サイトリンク・ロゴ画像) → DB 保存
3. handle 入力・予約語チェック・正規化・変更不可制約
4. 公開名刺ページ `/<handle>` (登録不要で閲覧可)
5. カスタマイズ機能 (フォント・色・テンプレ選択)
6. QR コード生成 (公開URL→PNG/SVG、ダッシュボード表示・DL)
7. vCard 3.0 ダウンロード (公開ページから .vcf)
8. 閲覧者の連絡先ローカル保存 (Dexie/IndexedDB) と一覧画面 `/saved`
9. 拡張領域 (ポエム・プロファイル・SNS リンク) 入力と表示

### P1 (MVP に含める)
10. 公開ページ「もっと見る」モーダル → 拡張領域表示
11. アクセスログ集計 (DB 記録 + ダッシュボードに簡易グラフ)
12. テンプレートパッケージ (3-5 種、JSON テーマ + Tailwind v4 `@theme`)
13. 印刷機能 (`/dashboard/print` 単票 91x55mm + A4 量産 2x5)

### Out of scope (MVP 外)
- 名刺の複数枚所持 (1ユーザー = 1名刺)
- チーム機能・組織共有
- 名刺の OCR 取り込み
- 課金・プラン
- 多言語 UI (日本語固定)
- メール本物配送 (dev は console.log、prod は別タスクで Resend/SMTP 切替)

### 5.1 Prisma schema (`prisma/schema.prisma`)

```prisma
generator client {

  provider = "sqlite"

  id        Int      @id @default(autoincrement())
```

#### 6.6.1 大文字混在 URL の正規化リダイレクト

URL に大文字や全角等が混じった場合、可能なら正規化後の handle へ **301 redirect** する。実装場所は **`src/app/[handle]/page.tsx` 冒頭 (Node runtime)**。

理由: middleware は edge runtime で Prisma 不可。DB 確認なしで盲目リダイレクトすると存在しない handle にも 301 が返り SEO/UX を損なうため、page 側で DB lookup を行ってから判定する。`src/app/[handle]/vcard/route.ts` も同じロジックを共有 (`/vcard` 付きのまま正規化先へ 301)。

判定ロジック (擬似コード):

```
const { handle: raw } = await params;
const normalized = normalizeHandle(raw);

// raw === normalized のケース
if (raw === normalized) {
  const card = await prisma.card.findUnique({ where: { handle: normalized } });
  if (!card || !card.isPublished) notFound();   // 404
  // → 公開ページ描画
}

// raw !== normalized のケース
else {
  if (!normalized) notFound();                    // 正規化結果が空 → 404
  const card = await prisma.card.findUnique({ where: { handle: normalized } });
  if (!card || !card.isPublished) notFound();    // 正規化先も無い → 404
  permanentRedirect(`/${normalized}`);            // Next.js 15 → 301
  // /vcard ルートでは permanentRedirect(`/${normalized}/vcard`)
}
```

挙動 (まとめ):

| 入力 raw | normalized | DB に normalized 存在 | 結果 |
|---|---|---|---|
| `yamada` | `yamada` | ○ | 200 公開ページ |
| `yamada` | `yamada` | × | 404 |
| `Yamada` | `yamada` | ○ | 301 → `/yamada` |
| `Yamada` | `yamada` | × | 404 |
| `YAMADA.taro` | `yamadataro` | ○ | 301 → `/yamadataro` |
| `日本語` | `` (空) | — | 404 |
| `--abc--` | `abc` | ○ | 301 → `/abc` |
| `login` | `login` | (予約語、DB に無い) | 404 |

注意:
- `permanentRedirect()` は `next/navigation` から import (Next.js 15 で `RedirectType.permanent` 同等)
- 301 は browser/CDN にキャッシュされるため、handle 変更不可制約と整合 (将来 handle を mutable にする場合は本ロジック再設計)
- `/saved` などアプリ内固定ルートは `[handle]` よりルーティング優先度が高い (App Router の物理ファイルが優先) ため、本ロジックは衝突しない

## 9. handle 仕様 (`src/lib/handle.ts`)

```ts
export const RESERVED_HANDLES: ReadonlySet<string> = new Set([
  "api","_next","static","public","favicon.ico","robots.txt","sitemap.xml",
  "login","signup","signout","auth","settings","profile","admin","dashboard",
  "help","legal","about","terms","privacy","u","c",
  "onboarding","verify-request","saved",
]);

/** 入力をハンドル候補に正規化する。形式違反は空文字を返す */
export function normalizeHandle(input: string): string {
  return input
    .normalize("NFKC")
    .toLowerCase()
    .replace(/[^a-z0-9-]/g, "")
    .replace(/^-+|-+$/g, "")
    .replace(/-{2,}/g, "-")
    .slice(0, 30);
}

/** 形式チェック (HandleSchema と同じ) */
export function isValidHandle(s: string): boolean { /* zod 結果に従う */ }

/** 予約語チェック */
export function isReservedHandle(s: string): boolean {
  return RESERVED_HANDLES.has(s);
}
```

挙動:
- 入力 `"Yamada.Taro"` → 正規化後 `"yamadataro"`
- 入力 `"--abc--"` → `"abc"`
- 入力 `"AB"` → `"ab"` (長さ 2 で zod 不合格)
- 入力 `"日本語"` → 正規化後 `""` で不合格
- 入力 `"login"` → 形式 OK だが reserved で不合格

### 10.6 vCard ビルダー (`src/lib/vcard.ts`)

```ts
export function buildVcard(card: {
  lastName: string; firstName: string;
  lastNameKana?: string | null; firstNameKana?: string | null;
  company?: string | null; department?: string | null; jobTitle?: string | null;
  phone?: string | null; email?: string | null;
  postalCode?: string | null; address?: string | null;
  websiteUrl?: string | null;
  logoUrl?: string | null;       // 公開URL (PUBLIC_BASE_URL 結合済み)
}): string;
```

仕様:
- vCard 3.0 ヘッダ
- `N:<lastName>;<firstName>;;;`
- `FN:<lastName> <firstName>` (半角スペース)
- 振り仮名がある場合のみ `X-PHONETIC-LAST-NAME:` `X-PHONETIC-FIRST-NAME:` を追加
- `ORG:<company>` (department があれば `ORG:<company>;<department>`)
- `TITLE:<jobTitle>`
- `TEL;TYPE=WORK,VOICE:<phone>`
- `EMAIL;TYPE=INTERNET:<email>`
- `ADR;TYPE=WORK:;;<address>;;;${postalCode};Japan` (postal は ZIP 位置)
- `URL:<websiteUrl>`
- `PHOTO;VALUE=URI:<logoUrl>` (ローカル URL でも OK、相手取り込み時に表示されない場合あり)
- `END:VCARD`
- 改行は `\r\n`、空フィールドは行ごと省略
- 文字エスケープ: `,` `;` `\` を `\,` `\;` `\\` に変換、改行 `\n` は `\\n` リテラル

```ts
import { normalizeHandle } from "@/lib/handle";

export default async function Page({
  params,
}: { params: Promise<{ handle: string }> }) {
  const { handle: raw } = await params;
  const normalized = normalizeHandle(raw);

  ...

import { permanentRedirect } from "next/navigation";
```

## 15. 挙動仕様 (Reviewer のテスト根拠)

### 15.1 handle 正規化
- `"YAMADA"` を入れると正規化結果 `"yamada"` で保存される
- `"yamada-taro"` は形式 OK、保存可
- `"-yamada"` は zod 不合格でエラー
- `"yamada--taro"` は連続ハイフンで zod 不合格
- `"login"` は予約語で `409 handle taken`
- `"abc"` (3文字) OK、`"ab"` (2文字) 不合格、31文字以上は不合格

### 15.2 onboarding
- 未ログインで `/onboarding` 直叩き → `/login` リダイレクト
- ログイン後 Card 未作成で `/dashboard` 叩く → `/onboarding` リダイレクト
- onboarding 完了 (POST 成功) → `/dashboard` リダイレクト
- 既に Card あるユーザーが `POST /api/card` → 403

### 15.3 公開ページ
- DB に `yamada` が存在する状態で `/yamada` → 200、公開ページ表示
- DB に `yamada` が存在する状態で `/Yamada` → **301 redirect、Location: `/yamada`**
- DB に `yamada` が存在する状態で `/YAMADA.taro` → 正規化後 `yamadataro` は DB に無い → **404** (異なる正規化先になるため redirect しない)
- DB に `yamadataro` が存在する状態で `/YAMADA.taro` → **301 redirect、Location: `/yamadataro`**
- DB に存在しない handle (例: `/notexist`) → 404
- 正規化後が空文字になる入力 (例: `/日本語`、`/--`) → 404
- 予約語 (例: `/login`) は DB に存在し得ない → 404 (App Router の物理ルート `(auth)/login` が優先される場合もある)
- `isPublished === false` の Card → 404 (raw === normalized でも、raw !== normalized で redirect 先が unpublished でも同じく 404)
- `/<handle>/vcard` でも同じリダイレクトロジックが働く (`/Yamada/vcard` → 301 → `/yamada/vcard`)
- 拡張領域 (poem/profile/snsLinks) が全て null → 「もっと見る」ボタンを描画しない
- vCard ダウンロードした内容を iOS 連絡先取り込み → 振り仮名 (X-PHONETIC-*) があれば五十音セクション正しい

### 15.4 vCard
- 振り仮名が空文字または null → `X-PHONETIC-*` 行を出さない
- `lastName` に `;` を含む → `\;` にエスケープ
- `email` 未入力 → `EMAIL` 行を出さない
- `Content-Type` に `; charset=utf-8` が含まれる
- レスポンスの先頭 3 byte が UTF-8 BOM (`EF BB BF`) でない

### 15.5 QR
- `generateQrPngDataUrl(url)` の戻り値が `data:image/png;base64,` で始まる
- `generateQrSvgString(url)` が `<svg` で始まり `</svg>` で終わる

### 15.6 ロゴアップロード
- 2MB ちょうどは 200、2MB + 1byte は 400
- `image/gif` は 400
- 拡張子は MIME から決定し、ファイル名のオリジナル拡張子は使わない (`logo.png` 固定形)
- 同 userId の再アップロードは前ファイル上書き

### 15.7 アクセスログ
- 公開ページ訪問で `Hit` が 1 件挿入される
- UA `Mozilla/5.0 (compatible; Googlebot/2.1...)` は挿入されない
- iPhone UA は `uaClass = "ios"`
- 同一ユーザーが 1 ページで何度リロードしても、その回数だけ Hit が増える (重複排除なし)
- `getStats(userId)` は自分の Card の Hit のみ返す (他人のカウントを混ぜない)

### 15.8 認証
- `AUTH_TEST_MODE=false` で Credentials Provider が **存在しない**
- `AUTH_TEST_MODE=true` で `signIn("test-credentials", { email: "x@x.jp" })` がセッションを発行
- Magic Link を `EMAIL_SERVER_HOST` 未設定時に投げると、コンソールに URL が 1 行出力される

### 15.9 Dexie / `/saved`
- 保存ボタン押下後、`db.contacts.count()` が +1
- 同 handle で 2 度押すと count は変わらない (上書き)
- 削除ボタン押下後、その行が消えて count が -1
- ブラウザリロード後も一覧が保持される

### 15.10 印刷
- `single` モードで `@page { size: 91mm 55mm }` のスタイルが DOM に注入されている
- `a4grid` モードで `.a4grid` 要素が 1 つ存在し、その中に `PublicCard` が 10 個並ぶ

## 19. コードコメント方針 (3LLM 並列レビュー意識)

設計docを **正典** とし、実装側のコメントは最小限に留める。

ルール:
- **書かない**: 関数の責務説明 (= 設計doc にある)。`// ユーザーを取得` のような日本語要約。
- **書く**:
  - WHY (設計doc にも書ききれない実装上の理由) ── 例: `// 型推論を効かせるため satisfies ではなく as const`
  - 設計doc 参照ポインタ ── 例: `// 設計 §10.6 vCard ビルダー`
  - 既知の罠 ── 例: `// fs.readFile は Node runtime のみ。route.ts の runtime export を確認`
- 関数の引数型・戻り値型は **TypeScript で表現**し、JSDoc は書かない (型が二重ソースになる)
- TODO/FIXME は禁止 (issue 化するか設計に戻す)

理由:
- Reviewer 3LLM が同一コードを独立に読むとき、コメントが「何を書いているか」を語ると LLM の判断材料がブレる。型と設計docだけ見れば一意に決まる状態を作る。

## 20. 不採用案

| 案 | 却下理由 |
|---|---|
| **Supabase / Firebase** | MVP DoD が「ローカル単体起動」。外部依存を入れると DoD が壊れる。 |
| **NextAuth v4** | Next.js 15 + App Router + Edge middleware の split-config が v5 で大幅改善。v4 は middleware で Prisma を扱う回避策が汚い。 |
| **vCard 4.0** | iOS18/Android16 でも 4.0 は互換が不安定。3.0 + `X-PHONETIC-*` で十分 (knowledge: vcard-japanese)。 |
| **localForage** | Dexie の `useLiveQuery` でリアクティブ一覧が一行で書け、IndexedDB 直叩きより堅い。 |
| **Umami / Plausible / GA** | 自前 `Hit` テーブルで MVP 要件 (訪問数表示) は満たせ、外部依存ゼロを保てる。 |
| **cva / tailwind-variants** | 5 テンプレ程度なら JSON テーマ + Tailwind v4 `@theme` で十分。バリアント抽象は YAGNI。 |
| **Playwright** | chrome-devtools MCP で対話的に E2E が回せ、ヘッドレス CI を持たない MVP では Playwright を入れる固定費が高い。 |
| **画像リサイズ (sharp)** | Alpine native build を増やす。MVP は 2MB 上限で許容、リサイズは P2 で sharp 導入。 |
| **多枚名刺対応** | `User has many Card` にすると handle 競合と UI が複雑化。1ユーザー1名刺で要件を満たせる。 |
| **handle 変更可能化** | リダイレクト履歴が必要となり実装複雑度が跳ねる。README 規約で「変更不可」と明記済。 |
| **国判定 (geoip-lite 等)** | DB ファイル数十MB が MVP image を肥大化させる。MVP は country=null。 |
| **Resend API (dev でも)** | 環境構築コストが上がり「単体ローカル起動」が崩れる。dev は console.log、prod のみ Resend/SMTP に切替。 |
| **WebAuthn (Authenticator モデル)** | Magic Link + Google で十分。後続フェーズで追加可。 |

## 23. Leader 判断済み事項 (旧オープンクエスチョン)

設計レビュー時点で挙がった 4 件、Leader が判断済み。本設計はこれらを織り込み済み。

| # | 項目 | 判断 | 反映先 |
|---|---|---|---|
| 1 | handle の最小文字数 | **3 を採用** (現状維持) | §5.2 `HandleSchema.min(3)`、§9、§15.1 |
| 2 | ロゴ画像のリサイズ | **しない / 上限 2MB のみ** (sharp 導入せず) | §10.4、§15.6、§20 (不採用案: 画像リサイズ) |
| 3 | A4 印刷レイアウト | **2列×5行 = 10枚** | §1 (P1)、§13、§15.10 |
| 4 | 公開URL の大文字混在 | **404 ではなく 301 redirect に変更**。raw !== normalize(raw) かつ正規化後が DB に存在すれば `/${normalized}` へ permanent redirect、無ければ 404 | §6.6.1 (新設)、§10.11、§15.3 |

判断 4 の補足:
- 実装場所は **page (Node runtime)** を採用 (`src/app/[handle]/page.tsx` および `src/app/[handle]/vcard/route.ts`)
- middleware は採用しない (edge runtime で Prisma 不可、DB 確認なしで盲目 redirect すると存在しない handle にも 301 が返り SEO/UX を損ねる)
- handle が変更不可 (immutable) である現設計と整合 (301 のキャッシュ問題が発生しない)
